新东方等平台客户 ·「无腾讯云账号」接入 CloudBase 连接器

专家内嵌「本地授权回调」方案设计 —— 消除跨应用跳转与手工复制密钥
场景 平台站外下发 envId + 环境 API Key 的下游用户 依赖 toolbox !32 / CLI !237 / weda-alternative !5799（已发布） 日期 2026-08-10

1. 背景与问题

公域插件（如 WorkBuddy）触发 tcb login --flow web 走统一登录态。但新东方这类平台客户的大部分下游用户没有腾讯云账号，他们的环境 ID（envId）与环境 API Key 由平台站外下发，无法走开发者账号登录。

已发布的三连 MR（toolbox !32 核心逻辑 + CLI !237 配合 + /login 页 !5799 的 API Key 表单）打通了 /login?cliAuth=1 的「环境 API Key 登录」入口：授权后经 localhost 回调把 envId+key 交回本地进程换临时 STS 凭证。但客户反馈操作链路太长：

目标：把「网页授权 + 复制粘贴」这一步在新东方自己的专家里完成 —— 由专家在本机起一个授权回调流程，静默拿到 envId + apiKey 并直接写入 toolbox 凭证文件；用户只剩「启用连接器」一个动作。

2. 已发布能力盘点（代码事实）

设计建立在以下已验证的机制上（源码在 cloudbase-toolbox/src/auth/）：

机制事实来源
授权 URL统一指向 https://tcb.cloud.tencent.com/login?cliAuth=1&_redirect_uri=<encoded>&authCallbackUrl=<127.0.0.1:port>&port=…&hash=…&mac=…&os=…&from=cli。回调地址由发起方自定端口，页面授权成功后 redirect 到该本地端口并携带 query。web-auth.ts
API Key 回调分支回调 query 带 authSource=api_key&envId=…&apiKey=… 时，本地进程调 exchangeApiKeyForCredential（POST https://<envId>.<region>.tcb-api.tencentcloudapi.com/capi/credential，Bearer apiKey）换临时 STS。web-auth.ts / api-key.ts
凭证落盘~/.config/.cloudbase/auth.json，结构 {_: 说明, credential: {tmpSecretId, tmpSecretKey, tmpToken, tmpExpired, envId, authSource:'api_key', apiKey}}。全局 / 项目级（projects/<cwd-hash>/）两级，读取顺序：项目级 → 环境变量 → 全局。localstore.ts / credential.ts
自动续期checkAndGetCredential 对 authSource='api_key' 的凭证：未过期直接用，过期后用落盘的 apiKey 重新换取；跳过 CheckTcbService 校验（临时密钥 policy 可能不含该权限，与 loginByApiKey 一致）。credential.ts:221
回调超时本地回调默认等待 600s（原 180s），覆盖用户选登录方式、填表时间。web/web.ts:138
CLI 非交互登录tcb login --cloudbase-api-key <key> -e <envId> 已支持无交互写凭证（无需 --flow web）。commands/account/login.ts
连接器侧WorkBuddy CloudBase 连接器 = npx @cloudbase/cloudbase-mcp@latest（现 v2.25.5），其 auth 工具已支持 action=login_by_api_key，且读取同一 toolbox 凭证体系 —— 写对 auth.json 即连接器可登录。connector mcp.json / cloudbase-mcp dist
会话加载MCP 工具在会话初始化时加载；连接器进程内 AuthSupervisor 为单例缓存。→ 启用/切换凭证后必须新开会话才生效。运行机制
核心洞察：本地回调机制并不绑定 CLI —— 它就是一个「起本地 HTTP 服务 → 打开授权页 → 收 query」的模式，_redirect_uri/authCallbackUrl 允许任意本地端口。因此新东方专家的 helper 可以完整复刻这一机制，把 envId+apiKey 静默落到凭证文件，用户全程不复制任何东西。

3. 目标方案总览

方案定位

新东方专家包内嵌一个 auth-bootstrap helper（自包含 Node 脚本 + 引导 Prompt）。用户在 WorkBuddy 会话里对专家说一句「我要连接 CloudBase」，专家即：起本地回调 → 打开授权页 → 收 envId+apiKey → 写凭证文件 → 引导启用连接器 → 提示新开会话。

交互变化

用户侧从 5 步（含复制密钥）降为 2 步：① 在会话里完成授权（粘贴平台下发的 key 一次，或走页面授权）；② 启用连接器并新开会话。密钥不再跨应用复制。

4. 凭证写入路径（三选一，按推荐排序）

回调拿到 envId + apiKey 后，落到 ~/.config/.cloudbase/auth.json 有 3 条路径，终点一致：

三条写入路径收敛到同一凭证文件，连接器无感复用
路径做法优点代价 / 前置
A · 推荐 helper 内嵌一个零依赖 Node 脚本：本地回调（复刻 web-auth.ts URL 构造）→ 调 /capi/credential 换 STS → 按 resolveWebCredential 的 tmp* 结构直接写 auth.json。 只需 node（WorkBuddy 自带运行时）；无网络安装依赖；UX/安全完全可控；离线环境可用 耦合凭证文件内部格式（envelope + tmp* 字段，需与库同步演进）
B · 库保证 helper 里 require('@cloudbase/toolbox')，调 AuthSupervisor.loginByWebAuth({flow:'web'}) 或 loginByApiKey(apiKey, envId)。 格式与换证逻辑由库保证，无需关心细节；API 一行完成 需能解析 @cloudbase/toolbox（临时 npm 安装或复用 CLI 依赖）；可能受网络/镜像限制
C · CLI 若用户环境已装 CloudBase CLI：tcb login --cloudbase-api-key <key> -e <envId>（非交互，一次到位）。 无需自研；老用户零学习成本；与官方行为 100% 一致 要求用户已装 node + CLI（npx 拉最新版亦可）；仍需拿到 key 后粘贴到终端
建议：专家包以 路径 A 为主实现（体验最顺、依赖最少），路径 B 作为探测到 toolbox 可解析时的升级分支，路径 C 作为「用户已有 CLI」时的快捷引导。三者写入的 auth.json 格式可被 resolveCredential 兼容读取。

4.1 capi 换证接口规格（路径 A 的换证实现参考）

路径 A 的 helper 需自实现换证逻辑，接口规格如下（与 exchangeApiKeyForCredential 完全一致，见 api-key.ts）：

项值
域名https://<envId>.<region>.tcb-api.tencentcloudapi.com（region 默认 ap-shanghai；整体可被环境变量 CLOUDBASE_API_ENDPOINT 覆盖，适配客户内网网关）
路径 / 方法POST /capi/credential
请求头Content-Type: application/json + Authorization: Bearer <apiKey>
请求体{"env": "<envId>"}
超时 / 代理15000ms；支持 HTTP 代理（getProxy）
成功响应{ "code": 0, "data": { "TmpSecretId", "TmpSecretKey", "Token", "ExpiredTime" } }
失败响应code !== 0 → 抛 CloudBaseError(message)（key 无效 / 环境无权限，登录即报错）
并发控制AsyncMerge 同 envId 5s 内合并请求，连点不重复打
curl -X POST "https://<envId>.ap-shanghai.tcb-api.tencentcloudapi.com/capi/credential" \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer <apiKey>" \
  -d '{"env": "<envId>"}'
  • ExpiredTime 是秒级时间戳，写盘前 ×1000 转毫秒存 tmpExpired。
  • 响应 data 直接是 STS 三要素，无二次包装；字段名以 Tmp* 开头，落盘后 SDK 直接可用。
  • helper 换证成功后按 resolveWebCredential 的 tmp* 结构写 auth.json（见第 2 节表格）。

5. 安全设计

  • 回调只信本地：helper 只监听 127.0.0.1 随机端口，一次性使用，收到回调立即关闭；_redirect_uri 不信任外部可控值，由 helper 自拼（与 CLI 现状一致）。
  • 密钥不落地明文日志：apiKey 打印时脱敏（前缀…后4位），不写入任何日志文件；helper 输出仅含 envId 与脱敏后的 key。
  • 凭证文件权限：写入后 chmod 600 auth.json（当前实现遵循默认 umask，建议 helper 显式收紧）。
  • 生命周期：apiKey 是环境级长期凭据，明文存于本机。与 loginByApiKey 现状一致；建议授权成功后引导用户在平台侧做 key 轮换 / 设置有效期。
  • 已知弱项（与 CLI 同款）：本地回调无一次性 state 校验，同机恶意进程可伪造回调注入自己的 key（后果 = 你的工具用了别人的环境，可被察觉）。建议后续在 /login 页支持透传随机 state 并回显校验，本次不阻塞。

6. 异常与回退

场景处理
用户已用账号登录过（auth.json 已有凭证）helper 先读 checkAndGetCredential，已有有效凭证则提示「已登录」；切换平台环境时明确覆盖并提示旧凭证失效。
回调超时（600s）提示重新发起；可支持 --no-browser 打印 URL 让用户手动打开（TCB_NO_BROWSER 同款）。
用户环境没有 node / 沙箱无运行时回退路径 C 引导（如有 CLI）；否则引导用户手动：启用连接器 → 新会话 → 调 MCP auth 工具 action=login_by_api_key 填入 apiKey+envId（该 action 底层即 loginByApiKey，已支持）。
平台只发 key、不发 envId 所在地域exchange 默认 ap-shanghai；envId 含地域前缀时自动识别，helper 支持 CLOUDBASE_API_ENDPOINT 覆盖。
连接器已启用但会话内工具未出现符合预期：MCP 工具会话加载 + 进程内凭证缓存 → 必须新开会话。helper 成功文案里内置该引导。

7. 落地清单（新东方专家包）

  1. 新增 skill：专家包 skills/cloudbase-auth-bootstrap/，含 helper.js（路径 A 自包含实现）+ SKILL.md（触发词：连接 CloudBase、启用连接器、环境 API Key 登录）。
  2. helper.js 职责：① 探测本地凭证状态；② 起本地回调服务并构造 /login?cliAuth=1 URL（复刻 web-auth.ts 参数）；③ 收回调解析 authSource/apiKey/envId；④ 调 /capi/credential 换 STS；⑤ 写 auth.json（tmp* 结构 + chmod 600）；⑥ 输出「授权成功 → 设置中启用 CloudBase 连接器 → 新开会话」引导文案。
  3. 专家 Prompt 引导：识别「连接/启用 CloudBase」意图 → 提示即将打开浏览器 → 执行 helper → 分步播报进度（起服务/等授权/换证/落盘）→ 收尾引导。
  4. 验收（首次启用后新会话）：在新会话用 MCP auth 工具查 status 为已登录；跑一次 queryEnv 或任一资源查询验证 envId 正确。
  5. 可选增强：helper 支持 --from-key 模式（用户直接把平台下发的 key 粘贴进会话，helper 跳过网页直接换证写盘）—— 专治「平台站外下发 key」场景，连浏览器都不用开。
总结：已发布的三连 MR 把「机制」备好了（任意本地进程可复用 /login?cliAuth=1 回调收 envId+apiKey），缺的只是「体验」——由新东方专家包内置 auth-bootstrap helper 补齐。用户在专家会话内完成授权，凭证直写 toolbox auth.json，之后仅剩「启用连接器 + 新会话」两步。无腾讯云账号不再是接入门槛。
